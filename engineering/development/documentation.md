# 文档维护

文档帮助使用者采用当前框架，也帮助维护者理解长期有效的设计。参考 Aruhaia 按架构、开发和路线组织文档的职责划分，不把任务执行过程当作项目知识。

## 位置与事实来源

| 内容 | 位置 | 事实来源 |
| --- | --- | --- |
| 框架介绍与采用导航 | 根 README、模块 README | 项目依赖、公开 API、可复现例子 |
| 安装、教程、功能限制与迁移说明 | docs 文档站 | 源码、测试、生成快照、打包元数据 |
| 当前架构、评估与 ADR | engineering/architecture | 源码路径、设计决定与适用条件 |
| 开发与验证方法 | engineering/development | 仓库脚本、CI 和 AGENTS |
| 重要目标、依赖、验收及当前状态 | engineering/roadmap | 当前实现和仍有效的约束 |

源码、项目文件、测试与打包信息优先于文字说明。历史内容不自动成为当前规则、任务状态或能力声明。

## 更新与索引

- 新增、移动或删除开发文档时，同步[工程索引](../README.md)与受影响入链。所有开发 Markdown 必须能从该索引沿链接找到。
- 路线图只保留重要目标、依赖、验收条件和简洁状态；复用已有条目，不要求每个任务或会话建立文档。
- 当前事实与目标设计明确区分。提案用“拟调整”“尚未实现”，不得把未来 API 写进当前快速开始。
- 重要设计连接源码位置、触发条件、影响和验收方式；源码变化使结论失效时，同步更新说明。
- ADR 记录背景、选择、代价和替代关系；不复制任务进度、命令输出和 agent 工作过程。
- 开发文档使用普通 Markdown；站点页面遵守 frontmatter、代码围栏和站内路由要求。不把工程评估加入公开站点侧栏或 sitemap。

## 过程记录边界

不创建、恢复或维护已停用的 `ai-plan/`。该目录的忽略项只保护已有私人残留，不代表它仍是工作入口，也不允许强制加入 Git。

不提交成对计划/追踪、tracking/trace、恢复文档、恢复点编号、分支映射、agent 交接、逐轮验证清单和执行流水。换成其他名字或搬入 `engineering/` 也不例外。多步骤工作和继续历史任务均不以生成这些文件为前提。

必要的临时探针、原始日志和本地笔记可使用忽略的 `.local/`，不强制生成。PR 或对话报告实际验证结果及未验证项；工程文档仅保留对后续维护有用的结论和限制。Git 保存源码与必要文档的变更，不额外提交一份过程日记，也不为清理旧留痕重写历史。

长期有效的约束继续由相应规则与设计负责：生成器与运行时隔离、标准资源所有权、发布版本语义和公开文档读者边界等。清理只涉及明确归属本任务的文件；保留其他任务、私人笔记、未跟踪文件和租约，不递归删除已停用目录。

## 验证

提交准备时核对文档索引可达性、相对链接、标题、代码围栏及删除目标的入链。公开页面运行仓库已有文档校验器并构建 VitePress。工程文档链接源码时检查文件和引用符号真实存在，不套用站点 frontmatter 检查。

本地链接与构建通过不证明正文准确；仍需核对 API、包依赖与可执行示例。维护入口不得要求创建已停用的计划或恢复文件。
