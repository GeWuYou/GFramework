# 文档维护

文档应帮助使用者采用当前框架，也帮助维护者理解设计依据。借鉴 Aruhaia 按架构、开发与路线组织的原则，不复制其产品规范、工具链或任务规模。

## 位置与事实来源

| 内容 | 位置 | 事实来源 |
| --- | --- | --- |
| 框架介绍与采用导航 | 根 README、模块 README | 项目依赖、公开 API、可复现例子 |
| 安装、教程、功能限制与迁移说明 | docs 文档站 | 源码、测试、生成快照、打包元数据 |
| 当前架构、评估与 ADR | engineering/architecture | 源码路径、明确设计决定与适用条件 |
| 开发与验证方法 | engineering/development | 仓库脚本、CI 和 AGENTS |
| 实施顺序、状态、验收及下一步 | engineering/roadmap | 实际 diff、验证结果和用户授权 |

源码、项目文件、测试与打包信息优先于文字说明。只在确有必要解释历史取舍时查 Git；旧文件中的“已完成”“当前 PR”“下一步”不自动成为现在的状态。

## 更新与索引

- 新增、移动或删除开发文档时，同步[工程索引](../README.md)与所有受影响入链。所有开发 Markdown 必须能从该索引沿链接找到。
- 同一任务的状态只放在路线图对应条目，不再维护成对计划/追踪、逐轮执行日志、分支映射或恢复点编号。
- 当前事实与目标设计必须明确区分。提案用“拟调整”“尚未实现”，不得把未来 API 写进当前快速开始。
- 每项重要评估连接源码位置、触发条件、影响和验收证据；修改源码导致结论失效时，在同一改动更新相关说明。
- ADR 记录背景、选择、代价和替代关系，不复制任务进度；任务结束后保留必要结论，细节由 Git 保存。
- 开发文档使用普通 Markdown；站点页面遵守 frontmatter、代码围栏和站内路由要求。不把工程评估加入公开站点侧栏或 sitemap。

只删除本任务工作树中列入 Git 的旧文档；私人笔记、其他分支、其他工作树与任务租约不在清理范围。旧路径的忽略项仅保护可能残留的私人文件，不再作为工作入口。历史基线通过 Git 提交查阅。

## 验证

提交准备时核对新增/删除清单、开发索引可达性、相对链接、标题和代码围栏；同步删除目标的入链。公开页面运行仓库已有文档校验器并构建 VitePress。工程文档链接源码时检查文件和引用的符号真实存在，不对源码文件套用站点 frontmatter 检查。

本地链接与构建通过不证明正文准确；逐项 review API、包依赖和可执行示例。全仓维护文件不得保留指向已删计划的有效导航。临时诊断和原始日志不复制到新文档树。
