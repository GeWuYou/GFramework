# ADR-001：标准 .NET 基础与可选编排

日期：2026-11-07。状态：已接受。核心和 Game 独立服务已按此方向实现；采用验收状态见[核心路线图](../roadmap/core-governance.md)。

## 需求与约束

框架由维护者个人使用，目标是通用 C# 应用底座。没有必须维持的第三方调用方；可以直接调整历史 API，不建设长期兼容双轨。仍保留 Game、Godot 和 ECS 的场景价值。

真正需要稳定的是：单例身份、服务作用域、初始化与释放责任、异步取消和宿主线程边界，而不是某一代基类名称或全局访问方式。

## 决定

采用 Microsoft DI 的注册、解析和所有权语义，以 Microsoft.Extensions.Logging 作为日志契约。普通服务应通过显式依赖工作，不要求继承框架基类、访问全局上下文或接受 Model/System/Utility 分类。

Architecture 作为可选模块装配和初始化编排保留；只有它提供的额外顺序、资源和宿主协作有明确消费者时才继续扩展。通用宿主集成按实际采用需要追加；Godot 等已有宿主驱动开始和停止。

CQRS 是按需应用能力，不作为通用核心的必选组成；Core 与 CQRS runtime 已解耦。现有本地事件与 request notification 的调用模型不同，不因都能“通知”就合并。

## 方案比较

| 方案 | 收益 | 长期成本 | 取舍 |
| --- | --- | --- | --- |
| 保持现有架构并不断包裹标准服务 | 短期改动少 | 继续维护注册期解析、正式 DI、全局上下文与自有日志之间的语义差异 | 不采用为长期方向 |
| 标准生态为基础，保留可选编排 | 明确资源责任，可独立采用能力，现有游戏宿主仍有接入点 | 需要一次破坏性迁移和宿主适配 | 采用 |
| 立即删除 Architecture 与全部角色抽象 | 表面最简，入口完全统一 | 尚未替代配置首载、模块阶段和宿主清理的实际作用，易产生新的重复装配代码 | 不采用 |

采用验证覆盖独立 C# 场景和现有 Godot 宿主；额外宿主适配按实际需求追加。

## 实施边界与代价

核心实现统一 provider 构建、实例激活与资源所有权，使用标准日志，并移除默认全局上下文依赖与旧消息执行器。Game 运行时采用普通服务，标准 DI 与可选 Architecture 使用相同实例；Godot 保留原生循环和显式 dispatcher。

UI 使用强类型路由、视图租约和默认宿主，场景、设置、存档与暂停通过显式依赖采用。破坏性 API 迁移同步更新仓库使用方、生成器、脚本模板和公开文档，不保留长期兼容双轨。

Godot appender、配置加载、协程、ECS 和资源管理保留已有能力。新设计不增加全量 schema、通用控件系统或未经测量的性能机制。Generic Host 集成与额外宿主按实际需求启动。

## 实践依据

- [Microsoft DI 指南](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines)：避免全局可变状态，明确容器创建对象的释放责任。适用于本项目两套解析路径与全局工厂问题；并不要求删除一切编排层。
- [Generic Host](https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host)：已有标准的应用启动和停止能力。复用于需要宿主的通用应用，不强加给引擎循环。
- [Martin Fowler 对 CQRS 的说明](https://martinfowler.com/bliki/CQRS.html)：完整 CQRS 应基于具体读写模型收益选择。本项目当前主要是内存消息 dispatcher，保留消息能力不意味着所有应用都要采用读写模型分离。
