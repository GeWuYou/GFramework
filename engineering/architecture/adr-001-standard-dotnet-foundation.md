# ADR-001：标准 .NET 基础与可选编排

日期：2026-11-07。状态：方向已接受，实现尚未完成。实施状态只见[核心路线图](../roadmap/core-governance.md)。

## 需求与约束

框架由维护者个人使用，目标是通用 C# 应用底座。没有必须维持的第三方调用方；可以直接调整历史 API，不建设长期兼容双轨。仍保留 Game、Godot 和 ECS 的场景价值。

真正需要稳定的是：单例身份、服务作用域、初始化与释放责任、异步取消和宿主线程边界，而不是某一代基类名称或全局访问方式。

## 决定

采用 Microsoft DI 的注册、解析和所有权语义，以 Microsoft.Extensions.Logging 作为目标日志契约。普通服务应通过显式依赖工作，不要求继承框架基类、访问全局上下文或接受 Model/System/Utility 分类。

Architecture 作为可选模块装配和初始化编排保留；只有它提供的额外顺序、资源和宿主协作有明确消费者时才继续扩展。Generic Host 是通用应用的可选宿主集成，Godot 等已有宿主自行驱动开始和停止，不额外运行 Host 循环。

CQRS 是按需应用能力，不作为通用核心的必选组成；当前尚未完成解耦。现有本地事件与 request notification 的调用模型不同，不因都能“通知”就合并。

## 方案比较

| 方案 | 收益 | 长期成本 | 取舍 |
| --- | --- | --- | --- |
| 保持现有架构并不断包裹标准服务 | 短期改动少 | 继续维护注册期解析、正式 DI、全局上下文与自有日志之间的语义差异 | 不采用为长期方向 |
| 标准生态为基础，保留可选编排 | 明确资源责任，可独立采用能力，现有游戏宿主仍有接入点 | 需要一次破坏性迁移和宿主适配 | 采用 |
| 立即删除 Architecture 与全部角色抽象 | 表面最简，入口完全统一 | 尚未替代配置首载、模块阶段和宿主清理的实际作用，易产生新的重复装配代码 | 本轮不采用 |

这不是预先建设 ASP.NET、桌面、插件、后台服务等全部适配器。先用一个独立 C# 场景验证基础语义，再按实际需求接入宿主。

## 实施边界与代价

首批统一 DI 构建、闭合资源生命周期、移除核心默认全局依赖。CQRS 包边界、历史命令 API、角色体系可选化和完整日志实现迁移分开进行。

现有 Godot appender、配置加载与格式化能力先保留；标准日志适配逐步接入，不能仅删除自有 ILogger 就丢掉输出能力。新设计不追求零依赖、全量 JSON Schema、Native AOT 承诺或未经测量的性能目标。

## 实践依据

- [Microsoft DI 指南](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines)：避免全局可变状态，明确容器创建对象的释放责任。适用于本项目两套解析路径与全局工厂问题；并不要求删除一切编排层。
- [Generic Host](https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host)：已有标准的应用启动和停止能力。复用于需要宿主的通用应用，不强加给引擎循环。
- [Martin Fowler 对 CQRS 的说明](https://martinfowler.com/bliki/CQRS.html)：完整 CQRS 应基于具体读写模型收益选择。本项目当前主要是内存消息 dispatcher，保留消息能力不意味着所有应用都要采用读写模型分离。
