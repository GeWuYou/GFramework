# 性能优化

先确定目标设备、代表性场景与可接受的帧时间、内存和加载延迟，再测量并定位热点。架构分层、DI、Result 或对象池本身不构成性能保证。

## 测量与比较

记录空闲、持续玩法、场景切换、存档、内容加载及退出时的指标。使用 Release 构建区分托管分配、GC、原生资源、CPU、GPU 与 I/O，保持输入与内容规模一致。重复观察稳定性；一个短探针不能证明长时间运行或全部设备表现。

构造注入使服务依赖在创建时确定，帧循环中直接使用已持有的能力。避免每帧解析容器、扫描程序集、反复创建订阅或重新反序列化同一配置。

## 资源与内存

资源租约明确持有时间，最后一次使用后归还；需要缓存命中率时采用预加载与手动驱逐，需要及时释放时使用自动策略。场景退出前先结束使用资源的对象，防止缓存清空与原生对象仍在使用发生冲突。

共享加载可以消除同键重复工作，但不会使不同资源加载自动并行，也不会降低底层资源本身的成本。载入策略与线程要求交由具体加载器和宿主确定。

## 事件与状态

Publish 在发布线程同步执行所有选定订阅者，回调的工作属于当前操作耗时。事件不是后台任务队列，长耗时工作应通过明确的异步操作管理，而不在回调中阻塞。

字段展示可以使用 BindableProperty；需要聚合 reducer、选择器或历史时再采用 Store。不要为了简单字段引入完整状态树，也不要每帧发布内容未变化的大快照。使用不可变结构时同样需要测量复制与分配成本。

## 对象池与协程

对象创建或释放是已测量热点时再池化。核对对象重置、最大保留容量、跨场景引用和重复归还，池化可能把短暂分配变成长时间内存占用。

协程采用显式所有者与作用域，退出时取消并等待必要清理。调度阶段与等待指令以[协程契约](../core/coroutine.md)为准；已有性能样例只能作为特定工作负载的可复现入口。
